# Research index

One line per finding, so a later session can decide what to open without reading each file.

- Why the keyboard draws under the navigation bar, and what Android does not say about it — apps targeting SDK 35+ are laid out edge-to-edge behind the system bars on Android 15+ with no opt-out by 36, and Hexboard targets 36; but the behaviour-changes page discusses Activities only and says nothing about `InputMethodService` input views either way, so the platform question stays open while the observed defect does not; `navigationBarsPadding()` is safe under either answer because the inset is zero where there is no bar; researched 2026-09-03 for `[board-under-navigation-bar]`. edge-to-edge-and-ime-input-views.md
- What Android gives a keyboard for voice input, and why a locale picker does not answer an accent complaint — an input method can recognise on-device from API 31 (forced from 33) with `RECORD_AUDIO`, proven by two existing keyboards, leaving API 26–30 uncovered; the selectable English set is organised by national variety and so reaches nobody whose accent comes from a first language; researched 2026-09-01 for `[in-keyboard-voice-input]`. android-voice-input-and-accents.md
- How much of a user's voice a speech model needs to adapt to them — the 30-minute figure applies only to full fine-tuning, which is the worst option at low data; LoRA adapts on minutes and beats it, embedding conditioning needs seconds, and one 2026 method needs no enrolment at all; gains are modest and measured on unrelated populations; **amended 2026-09-12** to split "no Android implementation" in two — sherpa-onnx is a packaged on-device Android runtime that streams and runs fine-tuned Whisper models, so running an adapted model has a route, while adapting one on the phone still has none; researched 2026-09-01 for `[personal-voice-model]`. speaker-adaptation-cost.md
- Which word list predictive text can ship — SCOWL's licence is permissive enough for a public PolyForm Noncommercial repo and it separates proper names into an excludable category, but carries no frequencies; its size levels may serve as a proxy, otherwise Leipzig (CC BY) is cleaner than wordfreq (CC BY-SA), and `hermitdave/FrequencyWords` is a licence trap; researched 2026-09-01 for `[uniform-neighbours-predictive]`, and amended 2026-09-17 with what SCOWL's own README says each size level contains — 60 is its recommended spell-checking size and the largest it is confident holds no misspellings, 70 is "large", 80 is Scrabble words and 85 is archaic, so the real choice is 60 or 70 and nothing above; and 2026-09-17 with Leipzig's terms read at source through the bot challenge — downloadable corpora are CC BY while the project's other data is CC BY-NC, the version number still second-hand, and automated queries prohibited. word-list-licence-and-frequency.md
- Whether a horizontal pager can wrap Hexboard's board-level tap detector for panel switching — `detectTapGestures` consumes the pointer-down, so the obvious wrap is a known hazard; two workarounds named (a non-consuming tap detector, or parent drag detection in the Initial pass), neither tested because Gradle cannot run here; researched 2026-09-01 for `[panel-switch-gestures]`. compose-pager-vs-board-tap-gesture.md
- How Gboard corrects dictated speech, and what matching it would take — it is an all-neural RNN-T recogniser and there is no separate autocorrect stage, correction happening inside recognition with optional language-model rescoring of the N-best hypotheses, so a corrector on a finished transcript has strictly less to work with; Gboard also personalises from saved on-device transcripts of what the user says and corrects, which is in tension with this project's storage posture; whether the public on-device API is the same engine is unresolved and testable; researched 2026-09-02 for `[speech-output-correction]`. gboard-speech-correction.md
- Whether a Cyrillic alphabet fits Hexboard's board — SUPERSEDED the same day: its 30-slot budget was wrong (26 letter positions once the function keys are counted) and the pair-the-overflow rule fell with it, in favour of copying Gboard's eleven-column Russian keyboard; the ЙЦУКЕН row contents and Ё-under-Е still stand, the phonetic Russian layout never investigated; researched 2026-09-02 for `[language-starter-layouts]`. cyrillic-overflow-and-slot-budget.md
- Where to transcribe each language's phone keyboard layout from, hidden letters included — FlorisBoard's Apache-2.0 JSON layouts and per-language popup files, read directly: its Russian file is the 11-11-9 ЙЦУКЕН rows Gboard shows, and its popups put ё under е and ъ under ь; AOSP LatinIME carries the same under indirections, the GPL forks are avoided on licence; **extended 2026-09-05** with the full 76-file layout catalogue, the finding that Portuguese and Italian have no layout file and differ from QWERTY only in their popup mappings, the four-tier cost model that orders languages by whether the config model can express the script rather than by speaker numbers, and a correction to its own risk line after the native-reader requirement was removed from SPEC; **extended again 2026-09-12** with the finding that FlorisBoard's symbol layouts are per script and region rather than per language, so it cannot say which quotation marks a language uses, and that CLDR's `delimiters` element supplies exactly the four quote characters per locale; researched 2026-09-02 for `[language-starter-layouts]`. open-source-layout-sources.md
- Licence options weighed for a public Hexboard — what each licence permits about reading, forking for other languages, and contributing back; researched 2026-08-04 for `[licence-and-go-public]`. licence-options.md
- Where an Android keyboard gets its emoji from — the Jetpack picker supplies list, skin tones and recents only through its own scrolling-grid view, its catalogue being internal (read from the library's declared API surface), so adopting it means abandoning Hexboard's five panels; Unicode's own `emoji-test.txt` gives the list in CLDR display order with groups and subgroups and no user interface, which is the road chosen, at the cost of building skin tones and recents here; the Unicode Terms of Use are flagged as NOT read; researched 2026-09-02 for `[emoji-panels]`. android-emoji-sources.md
- What a further language actually costs, and how optional assets reach a phone — a layout is 17 KB (measured, against the 640 KB emoji file already shipped) while its dictionary is a megabyte or two (estimated, not measured), so the two halves differ by orders of magnitude; SCOWL is English-only and the multilingual alternative is the Hunspell set, whose library is tri-licensed but whose per-language dictionary is a separate work with its own licence, making it one licence hunt per language; Play Asset Delivery can deliver optional assets after install with Google Play doing the fetching and the app making no network request, at the cost of publishing as an App Bundle through Play — and its documentation frames asset packs as a games feature, which is stated rather than glossed; researched 2026-09-05 for `[language-list-choice]`. language-cost-layouts-versus-dictionaries.md
- Where alternatives for an already-typed word could come from — key geometry cannot reach them (autocorrect has already fired by then, and "rose" for "rows" is two edits apart between two real words); an on-device language model is out because Google's ML Kit GenAI device list starts at the Pixel 9 while this project targets a Pixel 6 and API 26; `pimentel/homophones` is out for carrying no licence at all; what works is deriving homophone groups from CMUdict, whose licence makes any use unrestricted with acknowledgment requested, filtered to words already in the shipped list; researched 2026-09-04 for `[tap-word-alternatives]`. word-alternative-sources.md
- Whether Unicode's own data files may be bundled in a public repository and shipped in an app — yes: the Unicode License v3 is permissive in the MIT mould, granting use, copy, modify, publish, distribute and sell without restriction, on one condition, that the copyright and permission notice appear either with all copies of the data files or in the associated documentation; this clears the condition `[emoji-panels]` was left waiting on, and README's existing Notices section is the cheaper limb of that choice; researched 2026-09-04 for `[emoji-panels]`. unicode-data-file-licence.md
- Whether a keyboard can apply bold, italic and underline itself, and why none does — the plumbing is documented and supported: `GET_TEXT_WITH_STYLES` returns the selection with its styling and `commitText` takes styled text via `Spanned`, so read-toggle-commit is a supported round trip; what stops other keyboards is a position rather than an obstacle, that styling belongs to the app and the field, and a ProseMirror issue shows Gboard and rich web editors already disagreeing about spans inside a word, so web-based editors are the expected silent failure; the marker route that would reach them is a per-app table and was split off; which specific apps keep committed styling is NOT settled, nothing having been run on a handset; researched 2026-09-18 for `[selection-formatting-spans]`. keyboard-applied-text-styling.md
