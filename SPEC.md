# SPEC — Hexboard

## What this is

Hexboard (working name) is a virtual keyboard for Android. It's for people who are frustrated with the traditional keyboard layout, but it resembles that layout as closely as possible so the learning curve stays low.

## Who it's for

QWERTY users who want a better on-screen typing experience without having to relearn where the letters are. Familiar enough to adopt without a full relearning event — "open minds, but not so far open the brain falls out."

## How it works

The keyboard sacrifices row-straightness and uses circular keys in a neat hexagonal configuration. Rows zig-zag — odd columns sit half a key lower than even columns — and that trade-off is what yields greater key size than competing QWERTY-style virtual keyboards. Larger keys are the whole point.

The core differentiator is a **perceptual claim**: users feel more confident aiming at circular targets than at hexagons with visible corners. They aim more centrally, contact patches land closer to the key centre, and accuracy improves. This is what distinguishes Hexboard from existing tessellation-based keyboards (Typewise, MessagEase, Thumb-Key). The claim is settled as the project's direction, but it remains a testable one: it predicts something measurable about how people aim, and if user research showed the effect absent or too small to matter, the wedge would not survive it. Settled is not the same as proven. (Note: the claim is perceptual, not functional — Hexboard does not claim that hex keyboards mis-route taps.)

Layout details carried from the prototype:
- Otherwise plain QWERTY. Three letter panels sit side by side in the order RARE, QWERTY, SYMBOLS, with QWERTY as home: dragging the board left reaches SYMBOLS and dragging it right reaches RARE. Five emoji panels sit below the letters, reached by dragging the board up, and dragging back down returns to the keys. All three letter panels of a layout draw at one key size — the largest that fits the widest of them — and a narrower panel sits centred, so switching panels never resizes the board. Key size still varies between layouts, since a wider alphabet gets correspondingly smaller keys.
- Two space bars in row 3, one per thumb — a deliberate compromise that preserves layout familiarity at the cost of one mild oddity.
- The three letter panels are laid out side by side on one pitch, so the columns run continuously across the join from one panel to the next. Where the screen is wider than the board — a phone turned sideways, once the height bound below has made the board narrower than the screen — the current panel sits centred and the neighbouring panels show in the spare width. A key belonging to a panel that is not the current one is drawn but inert: it does not type and a tap on it does nothing, because a key that cannot be seen in full should not type and an accidental press should not move the board. **Key size is bounded by the height available as well as the width**, so that a sideways phone gets a keyboard rather than a screenful of keyboard — on a screen tall enough for the keys the width allows, nothing shrinks.
- A key is drawn as a soft-edged circle with no border: solid through the middle, then fading out to meet the fades of the keys around it, so no dead-looking space is left between them. The fade is what stops a board of large keys looking crowded, so a key is drawn at least as wide as it is tappable rather than sitting well inside it, and there is no hard boundary to aim within — only a soft target to aim at.
- Long-press accents cover diacritics for common letters plus alternate punctuation forms.
- Backspace and the cursor keys repeat while held; letters never do, since a held letter is its accent menu. Every hold on the keyboard — repeat, accent menus, anything later — waits the phone's own touch-and-hold delay and repeats at the phone's own rate, so a user who has slowed those down in Android's accessibility settings gets the same slowing here.
- Tapping shift capitalises the next character and then clears; tapping it twice in quick succession locks capitals, and a further tap clears both. Whichever state is on, the shift key is lit — differently for the two — and every letter, accent alternatives included, draws as a capital. With neither state on, letters draw in lowercase, so the board itself shows which state it is in.
- Uppercase glyphs render at 0.92× the lowercase font size, so capitals no longer overfill the circle relative to lowercase.
- Letter keys alternate between two resting colours from row to row, far enough apart to notice and nowhere near far enough to be mistaken for a press. The rows are still the QWERTY rows and only zigzag; the banding is what says so, and it runs across rows rather than columns because reading runs left to right. It is the letters that carry that recognition, so only they are banded — every other kind of key draws its own colour, and a row with no letters in it has no band.
- After a reboot Hexboard is unavailable until the phone has been unlocked once, so the unlock itself is typed on whatever keyboard the system falls back to. The keyboard's own state — the chosen layout, and later the saved words and the clipboard — lives in storage that is only readable after that unlock, and the clipboard deliberately so.
- While a physical keyboard is connected, Hexboard gets out of the way, and it returns when that keyboard is disconnected. This is Android's own behaviour for input methods and Hexboard does not override it.
- Press feedback is the key's own highlight and nothing else: the pressed key lightens instantly, holds, then fades back. Nothing marks where the finger actually landed, so a tap the nearest-centre routing absorbed is never drawn attention to.
- Intended hit-testing for Android: nearest-centre (Voronoi) assignment — full coverage, no gaps, no z-order tie-breaks.
- Accessibility: each key must expose its own accessibility node — an individually-focusable element with a text label and correct bounds — so screen readers and switch access work. **A key that types announces the character it will actually type in the state the board is currently in**, so a letter is announced lowercase with neither shift nor caps on and uppercase with either — the board shows its own shift state to anyone looking at it, and this is the same fact carried to someone who is not. A key that acts rather than types announces its action, and that name does not change. Accessibility services largely bypass raw-touch routing, so these nodes are a separate requirement from the nearest-centre hit-testing above; both must be correct.

Target stack: Kotlin / Jetpack Compose. The browser prototype (`hexboard17.html`) is frozen as the canonical reference for layout, gestures, and key inventory.

## Principles

- **The perceptual wedge is inviolable.** Any suggestion that compromises it (e.g. "just use rounded squares") should be questioned, not quietly accepted.
- **The key inventory is governed by config, never by code.** Which characters a layout offers and where they sit is stated in a config file and nowhere else — key data never lives in source. Every layout has a config of its own, one of them marked as the default the app ships with, and the four rules below bind each layout individually — so a further language adds one file and changes nothing else. Each config generates its own human-readable manifest, which is never hand-edited. The config carries the key inventory only — geometry stays in code, so a variant may change which characters exist but never the perceptual geometry. **The manifest governs the three letter and symbol panels and nothing else.** The emoji panels carry content taken from the Unicode standard's own published list and display order rather than an inventory curated here, so they are outside its scope: the four rules below do not apply to them, and their absence from the config is correct rather than a gap. The panels themselves are Hexboard's own — five of them, on Hexboard's geometry — while what fills them is not invented here, the same division the layouts already follow. **The five panels carry the commonest emoji in that published order, for fast reach without scrolling, and every other emoji is reached through a browser** that replaces the board area with a scrolling grid in Unicode's own groups and returns to the keys when one is chosen; the browser is opened from one of the panels' own slots, so it spends no gesture and no space above the keys. Four rules hold: no key may be lost (verify the shipped key set against the config before shipping); no unresolved duplicates (a character lives on one panel unless a second copy is deliberately justified — a long-press alternative is not a second copy, since it is not a key on a panel, so a character reachable both as a key and behind a hold is a convenience rather than a duplicate); no silent changes (any move, addition, or removal is reflected in the config and noted in the commit); and empty slots are opportunities, not acceptable gaps (a freed slot gets filled with a character that has no other home, agreed first). **A layout's quotation marks are the ones its own language uses**, taken from Unicode's published per-locale data rather than copied from English — and where that character already sits on another of the layout's panels, the slot takes the next character with no home instead of a second copy. **Every layout carries the five keys a keyboard needs** — shift, backspace, enter, and both cursor keys — whatever its alphabet costs in slots.
- **Hexboard ships a layout for each language it supports, copied from the standard phone keyboard for that language.** Because the geometry is inviolable and only the key inventory varies, a fix to the rendering reaches every layout at once. Layouts are not invented here: each is transcribed from the layout data of an open-source Android keyboard whose licence permits it — its row widths, its letter order, and which letters it hides behind a long-press — so what can go wrong is a transcription error rather than a bad design. Errors are caught by the people using the layout: the app carries a standing "Report a problem" entry that names the layout in use and lets someone say what is wrong, and a report is composed from a fixed set of fields carrying nothing the user has typed, shown to them, and sent by them from their own mail app rather than by Hexboard. A layout is not held back for a native reader's confirmation before it ships, because waiting on a reader who can be found for each language does not scale. Where that keyboard's rows are wider than ten keys, the layout's rows are wider too and its keys correspondingly smaller; no letter is hidden or dropped to make an alphabet fit ten columns. Every letter of the alphabet is reachable on its layout, visible or by long-press. Row 3, the zag rule and the circle geometry stay Hexboard's own on every layout. **Languages whose writing is not selected from a key inventory are out of scope** — Chinese, Japanese and Korean choose characters by conversion from what was typed rather than by pressing the character itself, which is an engine rather than a layout, and Hexboard does not offer one. **Where a language has more than one standard layout, Hexboard ships the one that language's phones most commonly show, and a further one when someone asks for it** — the same demand-driven rule the languages themselves follow. The exception is a language written in more than one script: there both ship, because a typist of the other script cannot type at all on the wrong one, where a typist given the less familiar arrangement of their own script can. Languages are added as they are asked for, and a language arrives in two parts. **Its layout ships inside the app** — every layout Hexboard supports is present in every install, because a layout is small. **Its word list does not**: word lists are large, so one arrives separately when the language is used, delivered without Hexboard making any network request of its own. A layout whose word list has not arrived is fully usable — the keys are right and typing works; only correction is absent. The user chooses their layout in the app's own settings rather than on the keyboard surface, so no typing gesture is spent on it and switching means leaving the text field; Hexboard announces itself to the system as one keyboard rather than one per language, so Android's own keyboard switcher offers Hexboard and not a list of its layouts, and there is one place a layout is chosen; the chosen layout is shown in the settings screen as a picture of the board, which does not type — the only thing on that screen that takes typing is the problem report's own field; layouts are offered grouped by language, the languages ordered by their own names as the device's language spells and sorts them, and ordered within a language by a set position, and nothing measures which layouts get used.
- **Predictive text is built rather than borrowed.** It corrects at the word boundary: pressing space compares the finished word against the dictionary and replaces it with the closest match, so no letter is trusted more than any other and a wrong first letter is no worse than a wrong last one. Closeness is measured with the key geometry — substituting a key for one of its six neighbours is a near-miss, any other substitution is a real difference — with ties broken by how common the candidate is. In a hexagonal tessellation each interior key has exactly six equidistant neighbours, which is what makes that measure uniform and meaningful. No general-purpose library can compute it, because none of them know which keys touch which; that is the reason to build the engine rather than adopt one. **What the engine recognises and what it may produce are two different sets.** Every word in the shipped dictionary is recognised, and so is never corrected, however uncommon it is; a correction may only ever produce a word from the commonest part of that dictionary, so a mis-tap is never turned into an obscure word that happens to sit one key away. Three rules bound the behaviour: a word already in the dictionary is never corrected; a correction is reverted by pressing backspace immediately after it lands; and the shipped dictionary carries no proper nouns, because a word corrected into a name is the most irritating failure autocorrect has. **The engine does not learn, and the only thing it stores is words the user has explicitly chosen to save.** It keeps no record of what has been typed, and infers nothing from it: the saved-word list grows only by a deliberate save, stays on the device, and is the user's to read and delete. A word is saved by tapping an offer that appears in the row above the keys at the moment a correction is undone, and the app's settings screen carries the list itself, where a word can also be added by hand, removed, or the whole list cleared. A saved word counts as a dictionary word: it is never corrected, and a near-miss is corrected toward it. **While a word is being typed, the middle of the row above the keys carries three slots: the exact string entered so far, and the two commonest words that could complete it, commoner first.** Tapping one puts that word in; nothing is applied unless it is tapped, and tapping the first of the three keeps what was typed without saving it. Completions read the word forwards, so a mistyped first letter simply leaves them blank — they offer, and the correction at the space bar is what acts. **Correction is per-language**: it uses the word list belonging to the layout being typed on, and where that layout has no word list the keyboard corrects nothing rather than correcting against another language's words. It was held until the keyboard itself worked, and that condition has been met.
- **Clipboard history persists rather than clearing.** Everything copied within the last hour is kept, however many items that is; beyond an hour, only the twenty most recent survive. History is reached by a button at the left-hand end of the row above the keys, and it replaces the board area rather than resizing the keyboard, so the text field never shifts; the same button returns to the keys. Tapping a clip pastes it and returns. An item is removed by holding it and dragging it to a bin that appears across the bottom while the drag lasts, and releasing anywhere else returns it to the list. There is no clear-all. Clips copied from a password field, and clips the source application marks sensitive, are kept for five minutes only, and the app states that rule where the user can read it. A clip copied while the keyboard is not attached to the field cannot be classified and falls under the ordinary rule. The store is encrypted at rest and never leaves the device.
- **Voice input lives inside the keyboard, and the microphone is held open by the user's thumb.** Speech is dictated without switching to another input method, so nobody has to switch away and forget to switch back. Recognition happens on the device and audio never leaves it; where a device cannot recognise on-device, voice input is unavailable rather than falling back to sending audio away. The microphone is open only while the control is held down, it is visibly indicated while open, and no audio is retained after the words have been transcribed. The control grows while it is held and shrinks when fully released, and released means the finger has left the screen rather than left the control, so a thumb drifting cannot cut a sentence short at any distance. **The board carries a row above the keys, and the microphone sits at its right-hand end**, drawn larger than a key and standing proud of that row; predictive text's suggestions share the row when they arrive. The microphone is not a key: it belongs to the board rather than to any layout's key inventory, so no language's config carries it and no layout can lose it. **Dictation leans toward the words the user has saved**, the recogniser being handed that list so a surname or a street name is likelier to be heard correctly; nothing about what was said is stored, and the separate switch that would bring the phone's own contacts into recognition is deliberately left off. **Dictated words arrive punctuated and capitalised where the device can supply that**, because the recogniser is asked for it — Hexboard adds no punctuation of its own to a finished transcript, and where a device cannot supply it the words simply arrive unpunctuated.
- **Voice recognition is planned to adapt to its own user, and the adaptation happens on the phone.** Accent selection is not the answer: a list of English varieties reaches only speakers who match one of its entries, and misses the second-language speaker entirely. Adapting to the individual voice is what does not care where the speaker learned English. Enrolment audio never leaves the device, and it is destroyed once adaptation has run — the phone keeps the adapted model and no recordings. Deferred until voice input itself works.
- **Nothing correctly spelled is ever changed on the user's behalf.** Hexboard corrects mis-taps; it does not correct grammar or punctuation. A word the user spelled correctly is left exactly as typed, however the sentence around it reads — so an apostrophe is never added to or removed from a real word, and no substitution is made on the strength of a judgment about the surrounding sentence. Offering an alternative the user can tap is permitted; applying one is not. This binds every route by which a finished word could be altered — the predictive engine, corrections to dictated text, and alternatives offered for a word already typed. **Tapping a word already in the text offers its homophones in the row above the keys, and tapping one replaces it.** The alternatives are words with the same pronunciation; no word is marked as wrong, and nothing changes unless the user picks a replacement.
- **Familiarity over radical departure.** Keep it close enough to QWERTY that users adopt it without relearning.
- Single dark theme is enough for v0; theming and customisation come later.

## Goals

- **Hexboard comfortably replaces Gboard for the person building it.** That is the bar the perceptual claim has to clear in practice rather than in argument: a keyboard that is interesting to use is not the same as one you keep using.
  Reached when: Hexboard has been the only keyboard on the project owner's phone for two unbroken months, with no switch back to Gboard to get something finished. Their own estimate was a month or two; two is written here because it is the harder of the two and a goal is meant to be a test.
