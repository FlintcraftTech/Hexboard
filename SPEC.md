# SPEC — Hexboard

## What this is

Hexboard (working name) is a virtual keyboard for Android. It's for people who are frustrated with the traditional keyboard layout, but it resembles that layout as closely as possible so the learning curve stays low.

## Who it's for

QWERTY users who want a better on-screen typing experience without having to relearn where the letters are. Familiar enough to adopt without a full relearning event — "open minds, but not so far open the brain falls out."

## How it works

The keyboard sacrifices row-straightness and uses circular keys in a neat hexagonal configuration. Rows zig-zag — odd columns sit half a key lower than even columns — and that trade-off is what yields greater key size than competing QWERTY-style virtual keyboards. Larger keys are the whole point.

The core differentiator is a **perceptual claim**: users feel more confident aiming at circular targets than at hexagons with visible corners. They aim more centrally, contact patches land closer to the key centre, and accuracy improves. This is what distinguishes Hexboard from existing tessellation-based keyboards (Typewise, MessagEase, Thumb-Key). The differentiator is settled — not to be re-litigated. The claim is settled as the project's direction, but it remains a testable one: it predicts something measurable about how people aim, and if user research showed the effect absent or too small to matter, the wedge would not survive it. Settled means it is not re-argued from the armchair, not that it has been proven. (Note: the claim is perceptual, not functional — Hexboard does not claim that hex keyboards mis-route taps.)

Layout details carried from the prototype:
- Otherwise plain QWERTY. Three letter panels (RARE / QWERTY / SYMBOLS) reached by horizontal swipe, with QWERTY as home. Five emoji panels reached by vertical swipe down.
- Two space bars in row 3, one per thumb — a deliberate compromise that preserves layout familiarity at the cost of one mild oddity.
- The visible circle is intentionally smaller than the touch target — a bigger targeting zone, and less crowded aesthetics.
- Long-press accents cover diacritics for common letters plus alternate punctuation forms.
- Uppercase glyphs render at 0.92× the lowercase font size, so capitals no longer overfill the circle relative to lowercase. This is a scaling factor, not a shared font size; chosen by eye against the layout preview.
- Press feedback is the key's own highlight and nothing else: the pressed key lightens instantly, holds, then fades back. Nothing marks where the finger actually landed, so a tap the nearest-centre routing absorbed is never drawn attention to.
- Intended hit-testing for Android: nearest-centre (Voronoi) assignment — full coverage, no gaps, no z-order tie-breaks. (The prototype's overlapping square boxes are incidental, not the design.)
- Accessibility: each key must expose its own accessibility node — an individually-focusable element with a text label and correct bounds — so screen readers and switch access work. Accessibility services largely bypass raw-touch routing, so these nodes are a separate requirement from the nearest-centre hit-testing above; both must be correct.

Target stack: Kotlin / Jetpack Compose. The Android build is a fresh effort, not a line-by-line port. The browser prototype (`hexboard17.html`) is frozen as the canonical reference for layout, gestures, and key inventory.

## Principles

- **The perceptual wedge is inviolable.** Any suggestion that compromises it (e.g. "just use rounded squares") should be questioned, not quietly accepted.
- **The key inventory is governed by config, never by code.** Which characters a layout offers and where they sit is stated in a config file and nowhere else — key data never lives in source. `resources/key-layout.json` is the default layout the app ships with, and `resources/key-manifest.md` is a human-readable view generated from it, and is not hand-edited. Where other layouts exist as contributed variants, each is described by its own config and the four rules below bind each layout individually. Each variant is a config file of its own, alongside the default rather than inside it, carrying an identifier, a human-readable name, and generating its own manifest — so a contribution adds one file and changes nothing else. The config carries the key inventory only — geometry stays in code, so a variant may change which characters exist but never the perceptual geometry. **The manifest governs the three letter and symbol panels and nothing else.** The emoji panels are system-supplied content rather than a hand-curated inventory, so they are outside its scope: the four rules below do not apply to them, and their absence from the config is correct rather than a gap. Four rules hold: no key may be lost (verify the shipped key set against the config before shipping); no unresolved duplicates (a character lives on one panel unless a second copy is deliberately justified); no silent changes (any move, addition, or removal is reflected in the config and noted in the commit); and empty slots are opportunities, not acceptable gaps (a freed slot gets filled with a character that has no other home, agreed first).
- **Hexboard is a platform for layout variants, and variants arrive by contribution rather than by fork.** Other people are meant to build key sets for other languages and alternate character sets. Because the geometry is inviolable and only the key inventory varies, a variant is data — one config file — and needs no copy of the code: layouts are contributed into this repository and one app ships them all, with the user choosing theirs. This is what keeps variants in step, since a fix to the rendering code reaches every layout at once and nothing downstream has to be re-synchronised. The cost is accepted deliberately: contributions are reviewed on the way in, and the app must eventually let a user switch layouts. That choice is made in the app's own settings rather than on the keyboard surface, so no typing gesture is spent on it and switching means leaving the text field.
- **Predictive text is planned but deferred, and will be built rather than borrowed.** It corrects at the word boundary: pressing space compares the finished word against the dictionary and replaces it with the closest match, so no letter is trusted more than any other and a wrong first letter is no worse than a wrong last one. Closeness is measured with the key geometry — substituting a key for one of its six neighbours is a near-miss, any other substitution is a real difference — with ties broken by word frequency. In a hexagonal tessellation each interior key has exactly six equidistant neighbours, which is what makes that measure uniform and meaningful. No general-purpose library can compute it, because none of them know which keys touch which; that is the reason to build the engine rather than adopt one. The neighbour sets are derived rather than hand-maintained, from `resources/key-layout.json` together with the zag rule that lives in code — the config gives each key's row and column, and the zag parity determines which six keys actually neighbour it. So the neighbour table is computed at runtime from both, not stored in the config. Three rules bound the behaviour: a word already in the dictionary is never corrected; a correction is reverted by pressing backspace immediately after it lands; and the shipped dictionary carries no proper nouns, because a word corrected into a name is the most irritating failure autocorrect has. **The engine does not learn, and the only thing it stores is words the user has explicitly chosen to save.** It keeps no record of what has been typed, and infers nothing from it: the saved-word list grows only by a deliberate save, stays on the device, and is the user's to read and delete. Held until after the first working model — get the keyboard right first.
- **Clipboard history persists rather than clearing.** Everything copied within the last hour is kept, however many items that is; beyond an hour, only the twenty most recent survive. History is reached from a clipboard screen, and an item is removed by holding it and dragging it to a bin that appears. There is no clear-all. Clips copied from a password field, and clips the source application marks sensitive, are kept for five minutes only, and the app states that rule where the user can read it. A clip copied while the keyboard is not attached to the field cannot be classified and falls under the ordinary rule. The store is encrypted at rest and never leaves the device.
- **Voice input lives inside the keyboard, and the microphone is held open by the user's thumb.** Speech is dictated without switching to another input method, so nobody has to switch away and forget to switch back. Recognition happens on the device and audio never leaves it; where a device cannot recognise on-device, voice input is unavailable rather than falling back to sending audio away. The microphone is open only while the control is held down, it is visibly indicated while open, and no audio is retained after the words have been transcribed. The control grows while it is held and shrinks when fully released, so a thumb drifting slightly does not cut a sentence short.
- **Voice recognition is planned to adapt to its own user, and the adaptation happens on the phone.** Accent selection is not the answer: a list of English varieties reaches only speakers who match one of its entries, and misses the second-language speaker entirely. Adapting to the individual voice is what does not care where the speaker learned English. Enrolment audio never leaves the device, and it is destroyed once adaptation has run — the phone keeps the adapted model and no recordings. Deferred until voice input itself works.
- **Familiarity over radical departure.** Keep it close enough to QWERTY that users adopt it without relearning.
- Single dark theme is enough for v0; theming and customisation come later.
- Out of scope for early iterations: IME service polish (settings screen, language switching) — type first, polish after.
