# SPEC — Hexboard

## What this is

Hexboard (working name) is a virtual keyboard for Android. It's for people who are frustrated with the traditional keyboard layout, but it resembles that layout as closely as possible so the learning curve stays low.

## Who it's for

QWERTY users who want a better on-screen typing experience without having to relearn where the letters are. Familiar enough to adopt without a full relearning event — "open minds, but not so far open the brain falls out."

## How it works

The keyboard sacrifices row-straightness and uses circular keys in a neat hexagonal configuration. Rows zig-zag — odd columns sit half a key lower than even columns — and that trade-off is what yields greater key size than competing QWERTY-style virtual keyboards. Larger keys are the whole point.

The core differentiator is a **perceptual claim**: users feel more confident aiming at circular targets than at hexagons with visible corners. They aim more centrally, contact patches land closer to the key centre, and accuracy improves. This is what distinguishes Hexboard from existing tessellation-based keyboards (Typewise, MessagEase, Thumb-Key). The claim is settled as the project's direction, but it remains a testable one: it predicts something measurable about how people aim, and if user research showed the effect absent or too small to matter, the wedge would not survive it. Settled is not the same as proven. (Note: the claim is perceptual, not functional — Hexboard does not claim that hex keyboards mis-route taps.)

Layout details carried from the prototype:
- Otherwise plain QWERTY. Three letter panels (RARE / QWERTY / SYMBOLS) reached by horizontal swipe, with QWERTY as home. Five emoji panels reached by vertical swipe down. All three letter panels of a layout draw at one key size — the largest that fits the widest of them — and a narrower panel sits centred, so switching panels never resizes the board. Key size still varies between layouts, since a wider alphabet gets correspondingly smaller keys.
- Two space bars in row 3, one per thumb — a deliberate compromise that preserves layout familiarity at the cost of one mild oddity.
- Whenever the screen is wider than it is tall, the board splits into two halves with a gap in the middle, one half under each thumb. The halves keep their columns, zag and key size; only where they are drawn changes.
- A key is drawn as a soft-edged circle with no border: solid through the middle, fading to nothing at the edge of the area it accepts. The fade is what stops a board of large keys looking crowded, so a key is drawn as wide as it is tappable rather than sitting well inside it, and there is no hard boundary to aim within — only a soft target to aim at.
- Long-press accents cover diacritics for common letters plus alternate punctuation forms.
- Backspace and the cursor keys repeat while held; letters never do, since a held letter is its accent menu. Every hold on the keyboard — repeat, accent menus, anything later — waits the phone's own touch-and-hold delay and repeats at the phone's own rate, so a user who has slowed those down in Android's accessibility settings gets the same slowing here.
- Tapping shift capitalises the next character and then clears; tapping it twice in quick succession locks capitals, and a further tap clears both. Whichever state is on, the shift key is lit — differently for the two — and every letter, accent alternatives included, draws as a capital. With neither state on, letters draw in lowercase, so the board itself shows which state it is in.
- Uppercase glyphs render at 0.92× the lowercase font size, so capitals no longer overfill the circle relative to lowercase.
- Rows alternate between two resting key colours, far enough apart to notice and nowhere near far enough to be mistaken for a press. The rows are still the QWERTY rows and only zigzag; the banding is what says so, and it runs across rows rather than columns because reading runs left to right.
- While a physical keyboard is connected, Hexboard gets out of the way, and it returns when that keyboard is disconnected. This is Android's own behaviour for input methods and Hexboard does not override it.
- Press feedback is the key's own highlight and nothing else: the pressed key lightens instantly, holds, then fades back. Nothing marks where the finger actually landed, so a tap the nearest-centre routing absorbed is never drawn attention to.
- Intended hit-testing for Android: nearest-centre (Voronoi) assignment — full coverage, no gaps, no z-order tie-breaks.
- Accessibility: each key must expose its own accessibility node — an individually-focusable element with a text label and correct bounds — so screen readers and switch access work. Accessibility services largely bypass raw-touch routing, so these nodes are a separate requirement from the nearest-centre hit-testing above; both must be correct.

Target stack: Kotlin / Jetpack Compose. The browser prototype (`hexboard17.html`) is frozen as the canonical reference for layout, gestures, and key inventory.

## Principles

- **The perceptual wedge is inviolable.** Any suggestion that compromises it (e.g. "just use rounded squares") should be questioned, not quietly accepted.
- **The key inventory is governed by config, never by code.** Which characters a layout offers and where they sit is stated in a config file and nowhere else — key data never lives in source. Every layout has a config of its own, one of them marked as the default the app ships with, and the four rules below bind each layout individually — so a further language adds one file and changes nothing else. Each config generates its own human-readable manifest, which is never hand-edited. The config carries the key inventory only — geometry stays in code, so a variant may change which characters exist but never the perceptual geometry. **The manifest governs the three letter and symbol panels and nothing else.** The emoji panels carry content taken from the Unicode standard's own published list and display order rather than an inventory curated here, so they are outside its scope: the four rules below do not apply to them, and their absence from the config is correct rather than a gap. The panels themselves are Hexboard's own — five of them, on Hexboard's geometry — while what fills them is not invented here, the same division the layouts already follow. Four rules hold: no key may be lost (verify the shipped key set against the config before shipping); no unresolved duplicates (a character lives on one panel unless a second copy is deliberately justified); no silent changes (any move, addition, or removal is reflected in the config and noted in the commit); and empty slots are opportunities, not acceptable gaps (a freed slot gets filled with a character that has no other home, agreed first).
- **Hexboard ships a layout for each language it supports, copied from the standard phone keyboard for that language.** Because the geometry is inviolable and only the key inventory varies, a fix to the rendering reaches every layout at once. Layouts are not invented here: each is transcribed from the layout data of an open-source Android keyboard whose licence permits it — its row widths, its letter order, and which letters it hides behind a long-press — and the transcription is confirmed by someone who reads the language before it ships. Where that keyboard's rows are wider than ten keys, the layout's rows are wider too and its keys correspondingly smaller; no letter is hidden or dropped to make an alphabet fit ten columns. Every letter of the alphabet is reachable on its layout, visible or by long-press. Row 3, the zag rule and the circle geometry stay Hexboard's own on every layout. Languages are added as they are asked for. The user chooses their layout in the app's own settings rather than on the keyboard surface, so no typing gesture is spent on it and switching means leaving the text field; layouts are offered grouped by language and ordered within a language by a set position, and nothing measures which layouts get used.
- **Predictive text is planned but deferred, and will be built rather than borrowed.** It corrects at the word boundary: pressing space compares the finished word against the dictionary and replaces it with the closest match, so no letter is trusted more than any other and a wrong first letter is no worse than a wrong last one. Closeness is measured with the key geometry — substituting a key for one of its six neighbours is a near-miss, any other substitution is a real difference — with ties broken by word frequency. In a hexagonal tessellation each interior key has exactly six equidistant neighbours, which is what makes that measure uniform and meaningful. No general-purpose library can compute it, because none of them know which keys touch which; that is the reason to build the engine rather than adopt one. Three rules bound the behaviour: a word already in the dictionary is never corrected; a correction is reverted by pressing backspace immediately after it lands; and the shipped dictionary carries no proper nouns, because a word corrected into a name is the most irritating failure autocorrect has. **The engine does not learn, and the only thing it stores is words the user has explicitly chosen to save.** It keeps no record of what has been typed, and infers nothing from it: the saved-word list grows only by a deliberate save, stays on the device, and is the user's to read and delete. Held until after the first working model — get the keyboard right first.
- **Clipboard history persists rather than clearing.** Everything copied within the last hour is kept, however many items that is; beyond an hour, only the twenty most recent survive. History is reached by a button at the left-hand end of the row above the keys, and it replaces the board area rather than resizing the keyboard, so the text field never shifts; the same button returns to the keys. Tapping a clip pastes it and returns. An item is removed by holding it and dragging it to a bin that appears across the bottom while the drag lasts, and releasing anywhere else returns it to the list. There is no clear-all. Clips copied from a password field, and clips the source application marks sensitive, are kept for five minutes only, and the app states that rule where the user can read it. A clip copied while the keyboard is not attached to the field cannot be classified and falls under the ordinary rule. The store is encrypted at rest and never leaves the device.
- **Voice input lives inside the keyboard, and the microphone is held open by the user's thumb.** Speech is dictated without switching to another input method, so nobody has to switch away and forget to switch back. Recognition happens on the device and audio never leaves it; where a device cannot recognise on-device, voice input is unavailable rather than falling back to sending audio away. The microphone is open only while the control is held down, it is visibly indicated while open, and no audio is retained after the words have been transcribed. The control grows while it is held and shrinks when fully released, and released means the finger has left the screen rather than left the control, so a thumb drifting cannot cut a sentence short at any distance. **The board carries a row above the keys, and the microphone sits at its right-hand end**, drawn larger than a key and standing proud of that row; predictive text's suggestions share the row when they arrive. The microphone is not a key: it belongs to the board rather than to any layout's key inventory, so no language's config carries it and no layout can lose it.
- **Voice recognition is planned to adapt to its own user, and the adaptation happens on the phone.** Accent selection is not the answer: a list of English varieties reaches only speakers who match one of its entries, and misses the second-language speaker entirely. Adapting to the individual voice is what does not care where the speaker learned English. Enrolment audio never leaves the device, and it is destroyed once adaptation has run — the phone keeps the adapted model and no recordings. Deferred until voice input itself works.
- **Nothing correctly spelled is ever changed on the user's behalf.** Hexboard corrects mis-taps; it does not correct grammar or punctuation. A word the user spelled correctly is left exactly as typed, however the sentence around it reads — so an apostrophe is never added to or removed from a real word, and no substitution is made on the strength of a judgment about the surrounding sentence. Offering an alternative the user can tap is permitted; applying one is not. This binds every route by which a finished word could be altered — the predictive engine, corrections to dictated text, and alternatives offered for a word already typed.
- **Familiarity over radical departure.** Keep it close enough to QWERTY that users adopt it without relearning.
- Single dark theme is enough for v0; theming and customisation come later.
- Out of scope for early iterations: IME service polish (settings screen, language switching) — type first, polish after.
