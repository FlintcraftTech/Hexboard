# [HASH] — The key config gains a variant identity, and the manifest generator stops assuming there is only one layout

SPEC says Hexboard is a platform for layout variants contributed into this repository, with one app shipping them all. `resources/key-layout.json` could not express that: it carried no field saying which layout it was, because it was written when there was exactly one. That single gap held two other pieces of work — an editor has to write a variant identifier and a picker has to read one — so this build closes it.

Three decisions, all made at the planning session that filed the item rather than here, were implemented as recorded. One file per variant: a contributed layout is a new file alongside `key-layout.json` rather than a section inside it, which is the whole reason contribution was chosen over forking. Identity fields: the config gains `id` (a stable machine name, here `qwerty-en`), `name` (what a person would see, "QWERTY (English)"), and a statement that this file is the layout the app falls back to when none is chosen — written as `isDefault: true`, with the `about` prose saying what the flag means so the field is not a bare boolean nobody can interpret. And the manifest follows the layout: the generator now reads the output path from the config's own `generates` field instead of a module-level constant, so a variant's manifest goes where that variant says.

Honouring `generates` is inert unless the script can be pointed at a config other than the default, so a `--config` option was added in the same file. This is the enabling half of the decision the item recorded rather than new scope: without it the field would be read and then always resolve to the one path it already used. It was tested by generating against a throwaway variant config in the session scratchpad, which correctly routed to that config's own `generates` path and exited 1 on the drift check, rather than writing over the default manifest.

The `about` rewrite folded into this item was the correction of a stale sentence rather than a new claim. That field still opened "This file is the single source of truth for which characters exist" — wording SPEC dropped on 2026-08-20 and narrowed again on 2026-09-01 to call this file the default layout the app ships with. The config was the last place the retired phrase survived. It now opens by describing one layout's inventory among several. Because the generator copies that prose into the manifest, regenerating is what carried the correction through, which is why the item asked for the regeneration rather than a hand-edit.

No Android code changed, as the item specified. Gson ignores JSON fields the data classes do not declare, so `KeyLayout.kt` parses the config unchanged and the app carries on loading the one layout it loads today. That reasoning was recorded on the item as the reason no Kotlin change was listed rather than as a tested claim, and this build did not test it either — Gradle cannot run on this machine.

The item's landing observation was met and checked: `python scripts/generate-key-manifest.py --check` reports no drift, and the manifest header names the layout. The manifest's diff against the previous commit is three lines, all header and intro — no key data moved, so SPEC's no-key-may-be-lost and no-unresolved-duplicates rules hold by construction.

The build stopped after this one item. The next cleared item, [repo-go-public], is marked `Runs alone`, so the run ended rather than carrying the same session's momentum into an irreversible outward-facing action.
