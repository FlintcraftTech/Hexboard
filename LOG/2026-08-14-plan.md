# 263eb26 — Go-public path cleared end to end: the owner-name drift fixed at source, the flip retagged from user-work to a single `gh` command after the premise proved false, the emoji question settled by scoping the manifest, and the keyboard build finally given queue items of its own

This session started from the previous one's advice to take [repo-go-public] next, and most of what follows came out of checking that item rather than trusting it.

**The owner name.** [github-org-case-drift] asked three questions and all three were answerable in-session, so the item was resolved and deleted rather than kept. GitHub's canonical spelling is `FlintcraftTech`, lowercase `c`, confirmed against the API through an authenticated `gh`; all six repositories sit under that one organisation, so there is a single owner name to get right rather than several drifting apart. Whether the case change was a deliberate rename or normalisation could not be distinguished and turned out not to matter — what matters is the string GitHub will accept. The drift was also smaller than the capture assumed: exactly three occurrences repo-wide, two in the [repo-go-public] walkthrough and one in an older LOG entry, and the capture's claim that the README's licence section named the owner was simply wrong. The two live occurrences were corrected and the git remote re-pointed, since it had been working only by GitHub's rename redirect. The risk that made this worth doing before the flip rather than after: GitHub's visibility dialog demands an exact match of the repository name, so the stale spelling would have been rejected mid-flip.

**The flip itself is no longer user-work.** While checking the owner name it emerged that `gh` on this machine is signed in with admin rights over the organisation, which falsifies the premise [repo-go-public] had rested on since it was split out — that going public was "an account action on github.com that Claude can't perform". Raised as a choice between filing it and working it in, and the user chose to work it in and to make the item Claude-run. The six-step browser walkthrough is replaced by one `gh repo edit --visibility public --accept-visibility-change-consequences` command; the consequences flag is mandatory, which is the kind of detail that would have stopped an unattended run. A two-sided verification was written in, because the authenticated view cannot report what an anonymous visitor sees: `gh repo view --json isPrivate` should read false, and an unauthenticated API request should return 200 rather than today's 404.

The retag deliberately does not change who decides. The item carries an explicit instruction to state what is about to become readable and get an explicit yes in the same session before the command runs. Retagging moved who types it and nothing else, and the item says so in those terms so a later session cannot read the `[user]` tag's removal as consent. It also carries `Runs alone`, so a run reaches it and stops rather than carrying its own momentum into an irreversible outward-facing action.

**An ordering fault of this session's own making, caught by the user's question.** Asked whether everything for going public was covered, the check turned up that [repo-go-public] had been placed after [run-key-config-validator] under the ordinary rule that user-work sits at the end of a region — but a run halts at a `[user]` item, so the flip would never have been reached unattended, and that validator test is not a gate for going public at all. The flip was moved ahead of it and the reasoning written into the item so a later re-sort does not silently undo it. It still sits behind [throughliner-doc-drift] and [emoji-panels-missing-from-config], because both correct text that going public publishes.

**The emoji question, settled.** [emoji-panels-missing-from-config] had recorded two readings of the same tension — either the emoji panels belong in the key config and are missing, or the manifest was only ever meant to govern the letter and symbol panels. The user chose the second: the emoji panels are system-supplied content, not a hand-curated inventory. SPEC was edited in-session to say so, because that is where the manifest principle lives and a planning decision that changes what SPEC says edits SPEC in the same session. The item survives, renamed to what it now does, because the same carve-out is still missing from three places SPEC does not reach — and the third of those was a genuine discovery: the generated manifest's intro prose and its four-rules preamble are hard-coded in `scripts/generate-key-manifest.py`, not read from the config's `about` field, so editing the config alone would have left the human-readable view contradicting SPEC.

**The queue had no item for building the keyboard.** [throughliner-doc-drift] flagged that three items sat below the readiness line without the blocker reference the current queue shape requires. Two of those waited on things in the world rather than on queue items, and filing those things exposed the gap: the key config, its validator and the audit that checks keys reach the screen were all queued, but the Compose keyboard they are all about was not. [compose-keyboard-renders-config] and [first-installable-build] now exist, and [android-key-audit] and [verify-a11y-ondevice] name them. Both new items were presented and skipped by the user's judgment that the central build deserves a session of its own rather than the tail of a planning one, which is right — designing it here would have been designing it tired.

**What was deliberately not done.** The rename half of [throughliner-doc-drift] was scoped to `CLAUDE.md` and `.gitignore` on the user's instruction to leave the LOG entries alone. The reason is worth keeping: a LOG entry records what a session actually said at the time, and rewriting it to use the method's new name would misreport that. The item now names the four live occurrences and states that everything else stays as written.

**On the go-public readiness question, one thing was refused rather than answered.** Every gate the item names was verified rather than trusted — the licence file is present, `FAQ/` is genuinely untracked, the commit identity is the noreply address, 73 files are tracked. Those were accepted deliberately at earlier planning sessions, not overlooked, and the honest position remains that not publishing is the only real protection.
