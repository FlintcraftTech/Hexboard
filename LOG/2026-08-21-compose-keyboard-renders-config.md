# [HASH] — The QWERTY panel drawn from the config on the real zag geometry, with the perceptual geometry given one Kotlin home

Until now the Android app was a template with a "Hello Android" greeting in it, and every piece of Hexboard that exists — the frozen browser prototype, the key config, the layout preview fixture — was about a keyboard that had never been drawn in Kotlin. This is the surface those things were waiting for, and four held queue items sit behind it.

The geometry is the substance. SPEC calls the perceptual wedge inviolable and the key config deliberately excludes geometry from itself, saying so in its own `about` field, so the rule needed exactly one home in Kotlin: `KeyGeometry.kt` now owns column parity, the gap and step sizes, the iterative radius solve, key centres, the visible-versus-touch radius, board dimensions, label sizing with the 0.92× uppercase scale, and nearest-centre hit-testing. Nothing else in the codebase computes a position. It was ported from `planning/layout-preview.html`, which carries the working parity and circle maths lifted from `hexboard17.html` — the porting question was never open, since SPEC already treats the prototype as specification for layout, gestures and key inventory.

Two decisions were made here that the item left open, and both are worth having on the record.

The first is how a tap finds its key. SPEC asks for nearest-centre (Voronoi) routing — full coverage, no gaps, no z-order tie-breaks — and it also asks that every key expose its own accessibility node with a label and correct bounds, noting that accessibility services largely bypass raw-touch routing. The intuitive Compose way to build a keyboard is to make each key a `clickable` circle, which satisfies the second requirement and quietly destroys the first: the drawn circle becomes the touch target, the gaps between circles answer to nobody, and the touch target stops being larger than what is drawn. So the two are separate mechanisms on purpose. The tap handler sits on the board and resolves by nearest centre; each key is a circle carrying a semantics node with a label, its own bounds and an `onClick` action for TalkBack and switch access. That is the intuitive-but-wrong alternative recorded with why it lost, so a later session does not restore it.

The second is smaller and would have bitten silently. Gson instantiates classes without running their constructors, so Kotlin default arguments never fire — a missing JSON field leaves a null sitting in a type declared non-null, and the crash arrives far from the cause. Every field the config may omit is therefore declared nullable and read through a non-null accessor.

The plumbing was further along than the item assumed: `android/app/build.gradle.kts` already copied `resources/key-layout.json` into the app's assets at build time. What it lacked was Gson on the main source set, which was `testImplementation` only; promoting it to `implementation` also leaves the existing validator test working, since a unit test's compile classpath includes the main implementation dependencies.

What has and has not been checked is the part of this entry to read carefully. Gradle cannot run on this machine — it needs a loopback connection to its own daemon, and every route available is blocked from making one, established across four attempts and recorded on [run-key-config-validator]. So nothing has compiled this code. What could be checked was checked properly rather than skipped: the geometry was reimplemented in Python and run against the real config, and it reproduces the prototype's own radius solver exactly at seven screen widths from 320 to 800dp, fills the width it is given, puts all forty QWERTY keys on forty distinct centres with every key's centre routing to itself, and gives an interior key exactly six equidistant neighbours at one vertical step with the next ring far beyond. That last one is the hexagonal property SPEC's predictive-text principle depends on, confirmed against real key data rather than assumed. Compilation, the Gson parse against the shipped asset, and the panel on screen are all still unverified, and are filed as [compile-and-view-panel].
