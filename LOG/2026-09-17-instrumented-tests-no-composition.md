# [HASH] — [instrumented-tests-no-composition] twelve failing instrumented tests resolved, none of them a fault in the keyboard: eight were the handset's screen going dark and four were the test file being wrong about the app

Recorded 2026-09-17 09:22, read from the clock. This session ran across 2026-09-12 and 2026-09-17.

Twelve of twenty-five instrumented tests failed on the Pixel 6 on 2026-09-09, every one of them a test that renders the board, each with `No compose hierarchies found in the app`. The item carried three hypotheses; one had already been eliminated at the desk, and the two survivors both accused the app — that `createComposeRule()` was the wrong rule for a board stood up outside an activity, and that something inside `HexboardBoard` threw under the harness and took the composition with it. Both are now dead, and the keyboard was never at fault.

**The desk pass first, because it narrowed the search before any device time was spent.** Three explanations that would have been cheap answers turned out to be already correct in the repository: `ui-test-manifest` is on `debugImplementation`, so `createComposeRule()`'s ComponentActivity is declared; the app manifest and the Compose and AGP versions are ordinary; and all seven UI test files use the same rule and call `setContent` before anything measures. That uniformity was itself the finding — a fault specific to one file could not produce it.

**A diagnostic split the two survivors in a single run.** A temporary `HarnessDiagnosticTest` climbed from a bare `Text` with no Hexboard code in it, to the board without emoji panels, to the board exactly as the failing tests build it. All three passed on their first run. That exonerated the rule and the board together, and left the difference between that run and the failing one as the only thing to explain: three tests in one class on an awake phone, against twenty-five across seven classes on a phone left to itself.

**Eight of the twelve were the screen.** A Compose test needs a resumed activity to have a composition to inspect; a dark screen means there is none, which is why every rendering test failed and every non-rendering test passed — a split that looks like a code fault and is not one. Re-running the suite with the phone awake took the failures from twelve to four. It then recurred inside this session's own verification run, because the suite takes about fifty seconds and the screen's timeout was shorter, which is what turned a one-off into a filed item.

**The remaining four were `EmojiPanelsUiTest` being wrong about the app, in three distinct ways.** It asked whether a key's `output` was on screen, where every key publishes its `label` — `"Q"` rather than `"q"` — so it fell at its first line before any gesture; the sibling test files already used `accessibilityLabel(key)`, which is what this one now does. It dragged *down* to reach the emoji panels, where SPEC places them above that gesture rather than below it, so the vertical pager had nowhere to go; that SPEC sentence had been corrected by `spec-emoji-swipe-wording` on 2026-09-12 and the test still carried the old wording, which is why the failure survived an awake screen. And it computed tap points from `KeyGeometry.centre`, which gives a point inside a *panel*, while the full board puts a control strip above that panel — so every tap was short by the strip's height and committed nothing. `KeyConfigUiTest` passed with the same arithmetic only because it renders a bare panel with no strip above it. The taps now read the key's own bounds from the board rather than predicting them, and stay raw touches rather than `performClick()`, because what these tests exist to catch is a pager consuming the pointer before the key sees it — the semantics click path would bypass exactly the routing under test.

**One failure survived all of that, and it was the mirror of the fix.** Dragging up reached the emoji panels; dragging back down did not return. `swipeDown()` on its own begins at the top of the board, which is the control strip and not part of the vertical pager, so the gesture was never handed to the pager — while `swipeUp()` begins at the bottom, already inside it. Starting the downward drag from the middle fixed it. Twenty-eight of twenty-eight now pass.

**An alternative considered and rejected at the close: keeping the diagnostic as a standing canary.** Its bare-`Text` test would fail fast and unambiguously the next time the screen sleeps, saving a reader four stack traces. It was deleted anyway, on the reasoning that it asserts nothing about the keyboard, so it can only fail for reasons the real tests also catch — the saving is in diagnosis time, not in coverage, and a test that exists to make other failures easier to read is a cost carried on every run for a benefit taken rarely. The user left the choice to Claude's recommendation.

**What this says about the item's own framing, worth carrying forward.** The item was written as a fault in the app or in the harness, and reasonable people wrote three hypotheses without any of them being the device's power settings. The evidence that identified it — a clean split between tests that render and tests that do not — was in the original report from the first line, and was read as pointing at the composition rather than at what the composition needs. The generalisation is narrow and deliberate: where a whole class of tests fails identically and a narrower run of the same code passes, the difference is in the run rather than in the code.
